jobs

This item only works when running on the server. Serverserver-util

The build job: what a chunk still owes the world, and the predicates and orderings the build loop asks about it.

A job lives on its own entity under the BuildJob component, so in-flight work is inspectable in Jabby rather than hidden in a module list.

Types​

BuildJob​

</>
interface BuildJob {
entity: Entity--

The entity this job is stored on, so a sorted job can still delete itself.

chunkX: number--

Chunk column.

chunkY: number--

Chunk row.

folder: Folder--

The chunk folder, used to test whether the job is still alive.

dest: Instance--

Parent for what this job builds.

runs: {Run}--

Wall runs still to build, farthest first; the build loop pops the last.

runSortKey: string?--

Observer positions the runs were last ordered against.

placements: {Placement}--

Prefabs still to build.

placementEntities: {Entity}--

Entity per placement, index-aligned with placements.

placementIndex: number--

Next placement, 1-based.

baseX: number--

Chunk origin column, in world cells.

baseY: number--

Chunk origin row, in world cells.

}

One unit of incremental build work.

jobs.track(

job: BuildJob--

Must already carry the entity it will be stored on.

) → ()

Stores a build job on the entity it already carries.

The job knows its own entity id because the build loop sorts the job list, and any parallel array of entities would desynchronise the moment it did.

sortFarthestFirst​

</>
jobs.sortFarthestFirst(
list: {BuildJob},--

Sorted in place.

playerChunks: {{
x: number,
y: number
}}--

Observer positions in chunk space.

) → ()

Sorts jobs farthest-observer-first.

The build loop consumes jobs from the end of the list, so farthest-first ordering is what makes the nearest chunk build first. Reversing this builds the far side of the world while the player stares at a hole.
